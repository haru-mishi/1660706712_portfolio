Haru AI Hub: a self-hosted LLM admin console

A web platform where a team can use AI chat models running on its own server, with per-user API keys, usage limits, and an admin panel.

Dashboard: active API keys, available models, and this month's token usage against the user's quota.

The problem

Cloud AI APIs cost money per request and send your data to a third party. A team that runs its own model (with Ollama) still needs the boring parts: accounts, keys, limits, and someone who can see who is using what.

What I built

A role-based web app with 6 core screens (login, dashboard, API keys, chat, profile, admin console), designed first in Figma with a documented design system so every screen uses the same colors, spacing, and components.

How it works

  • The backend talks to the local Ollama model over HTTP. It trims the conversation history to fit the model's context window, uses tuned sampling settings, and gives up cleanly after a 30-second timeout so a slow model can't hang the app.
  • Users see only their own keys and usage. Admins see everyone's accounts, models, and token consumption.
  • Every API key is scoped with an allow-list of models it may call, and model names are swappable references instead of hard-coded values.
  • User input and model output are sanitized (cleaned of unsafe content) to block injection attacks.

Tech used & why

Next.js + React
One framework for both the screens and the API routes, so frontend and backend live in one project.
Tailwind CSS
Made it quick to apply the design system consistently across all 6 screens.
Ollama
Runs open-source LLMs locally and exposes them over a simple HTTP API.

Thai Handwritten-Digit Recognition

Draw Thai numerals (๐–๙) on a canvas and a neural network I trained reads them back as numbers, including multi-digit numbers of any length.

Drawing ๕๖. The app splits the strokes into two digits and reads 56. The panel on the right shows how confident the model is in each digit.

The problem

Most handwriting models are trained on Arabic numerals (0–9). Thai numerals look very different, and people write multi-digit numbers with strokes that often touch, which makes it hard to tell where one digit ends.

What I built

A 10-class Convolutional Neural Network (CNN), a type of neural network designed for images, trained on about 3,880 handwritten images and served as a web app through a Flask API.

How it works

  • Data augmentation: during training I generated rotated, shifted, and scaled copies of each image, so the model learns shapes rather than memorizing exact pixels.
  • Simpler was better: removing the BatchNormalization layers improved accuracy on this small dataset. I tested it rather than assuming the textbook architecture was best.
  • Test-time augmentation: when predicting, the API checks several slightly altered versions of the drawing and averages the answers for a more stable result.
  • Touching digits: the Next Digit button sends an explicit "new digit starts here" flag, which solves cases that guessing by stroke distance can't.

Result

~92% of test digits the model had never seen were recognized correctly.

Tech used & why

TensorFlow
Used to build and train the CNN.
Flask
A lightweight Python web server that exposes the model at a /predict endpoint.
Python
Covers the whole pipeline, from image preprocessing to training to serving.

The live demo runs on a free server that sleeps when idle, so the first visit can take 30–60 seconds to load.

KFSuay: a concurrency-safe restaurant POS backend

A Point-of-Sale ordering backend for a restaurant chain that never sells more stock than a branch actually has, even when many orders arrive at the same moment.

After the rush test: 30 orders fired at once against 10 buckets in stock. The order log shows exactly 10 ACCEPTED and 20 SOLD OUT, and the item flips to sold out.

The problem

If two cashiers sell the last item at the same instant, a naive backend reads "1 left" twice and sells it twice. This is called a race condition, and it leads to overselling and negative stock.

What I built

A FastAPI order endpoint backed by PostgreSQL for a multi-branch POS, with a small register-style UI for the demo, all packaged with Docker Compose so it starts with one command.

How it works

  • Each order runs inside a database transaction, so all of its steps succeed or fail together.
  • SELECT … FOR UPDATE locks the stock row. A second order for the same item waits until the first one finishes, then sees the updated count.
  • As a second safety net, a database constraint rejects any change that would push stock below zero, even if the application code had a bug.
  • I wrote up the trade-off between pessimistic locking (lock first, used here) and optimistic locking (check for conflicts afterwards and retry) in a design document, along with a roadmap.

Result

10 / 20 A load script fires 30 simultaneous orders at 10 units of stock. Exactly 10 succeed, 20 are cleanly rejected, and stock never drops below 0.

Tech used & why

FastAPI
A fast Python API framework with automatic request validation and docs.
PostgreSQL
Provides the transactions, row locks, and constraints that make the guarantee hold.
psycopg
The Python driver I used to write the SQL by hand, so the locking stays explicit and easy to follow.
Docker
Anyone can run the API and database together with a single command.
